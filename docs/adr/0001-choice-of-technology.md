## Context (Контекст)

Архітектура CQRS розділяє write-модель (PostgreSQL) та read-модель (Redis). Синхронізація моделей і міжсервісна взаємодія (`Order Service → Access Service`, `Course Service → Catalog Query Service`) виконуються асинхронно через доменні події. SRS накладає на транспорт подій такі обмеження:

1. **Гарантія доставки At-Least-Once** без втрати подій при недоступності брокера до 5 хв ([SRS-NFR-REL-01](../srs.md#srs-nfr-rel-01)). Втрата `PaymentConfirmed` означає оплачений, але не виданий доступ.
2. **Порядок подій у межах агрегата**: `OrderCreated` має оброблятися раніше за `PaymentConfirmed` того самого замовлення.
3. **Перебудова read-моделі**: при зміні схеми Redis-проєкції або втраті даних Redis read-модель каталогу повинна відновлюватися повторним читанням історії подій без звернення до write-БД ([SRS-FUN-10](../srs.md#srs-fun-10)).
4. **Кілька незалежних консюмерів однієї події**: `course.events` споживають одночасно Catalog Query Service та Order Service (знімок ціни).
5. **Повторна обробка та DLQ**: 5 спроб з експоненційною затримкою, далі — DLQ з можливістю повторної публікації адміністратором ([SRS-FUN-20](../srs.md#srs-fun-20), [SRS-FUN-26](../srs.md#srs-fun-26)).
6. **Обмеження середовища**: Docker Compose на одному хості, 8 vCPU / 16 ГБ RAM ([SRS-NFR-ENV-01](../srs.md#srs-nfr-env-01)); цільове навантаження — 600 RPS на API, що відповідає ≈ 120 подіям/с у піку (20 % запитів — команди).

## Alternatives (Розглянуті альтернативи)

### A. Apache Kafka 4.x (KRaft, без ZooKeeper)

- Розподілений журнал (append-only log) з налаштовуваним строком зберігання; повідомлення не видаляються після споживання.
- Порядок гарантується в межах партиції; ключ партиції `aggregateId` забезпечує порядок подій одного агрегата.
- Consumer groups: кожен сервіс читає топік незалежно зі збереженням власного offset; повторне читання — через скидання offset (`kafka-consumer-groups.sh --reset-offsets`).
- Idempotent producer (`enable.idempotence=true`, `acks=all`) усуває дублікати на стороні запису в брокер.
- Обмеження: відсутні вбудовані відкладені повтори та DLQ — реалізуються на рівні застосунку (retry-топіки або повтори в консюмері). JVM-процес потребує ≈ 1–1,5 ГБ RAM. Одноброкерна конфігурація не забезпечує реплікації (replication factor = 1).

### B. RabbitMQ 4.x (AMQP 0-9-1, Quorum Queues)

- Брокер черг з маршрутизацією через exchanges; повідомлення видаляється після підтвердження (ack).
- Вбудовані механізми: Dead Letter Exchange, TTL повідомлень, publisher confirms; quorum queues забезпечують реплікацію на основі Raft.
- Порядок гарантується в межах однієї черги з одним консюмером; при конкурентних консюмерах порядок для агрегата не гарантується без додаткового шардування черг (consistent-hash exchange).
- Повторне читання історії неможливе для класичних і quorum-черг. RabbitMQ Streams (з версії 3.9) надають журнальну модель, але потребують окремого клієнта, а підтримка у NestJS-екосистемі (`@nestjs/microservices`) обмежена.
- Обмеження: перебудова read-моделі вимагає окремого механізму (повний експорт з PostgreSQL), тобто прямого зв'язку Query-контуру із write-БД, що порушує ізоляцію CQRS.

### C. Redis Streams (наявний Redis 7)

- Журнал повідомлень з consumer groups, `XACK`, `XPENDING`/`XCLAIM` для повторів; не потребує окремого контейнера.
- Обмеження: Redis є одночасно read-моделлю та брокером, тобто єдиною точкою відмови для двох функцій; довговічність залежить від налаштувань AOF (`appendfsync everysec` допускає втрату до 1 с даних); обсяг журналу обмежений оперативною пам'яттю.

## Decision (Рішення)

Обрано **Apache Kafka 4.x у режимі KRaft** як шину доменних подій.

Обґрунтування за критеріями SRS:

| Критерій | Kafka | RabbitMQ | Redis Streams |
| :--- | :--- | :--- | :--- |
| Повторне читання історії для перебудови read-моделі (обмеження 3) | Так, нативно (retention + reset offset) | Ні (лише через Streams-плагін) | Так, у межах RAM |
| Порядок подій агрегата при паралельних консюмерах (обмеження 2) | Так (ключ партиції) | Потребує шардування черг | Ні при кількох консюмерах у групі |
| Незалежні консюмери однієї події (обмеження 4) | Consumer groups | Окрема черга на кожного консюмера (fanout) | Consumer groups |
| Вбудовані DLQ та відкладені повтори (обмеження 5) | Ні — реалізується в застосунку | Так (DLX, TTL) | Ні |
| Ізоляція відмов брокера та read-моделі | Так | Так | Ні |
| Витрати RAM у локальному середовищі | ≈ 1–1,5 ГБ | ≈ 0,3–0,5 ГБ | 0 (наявний Redis) |

Пропускна здатність **не є аргументом вибору**: ≈ 120 подій/с обробляються будь-якою з трьох альтернатив. Вирішальними є обмеження 2 та 3: журнальна модель Kafka дозволяє відновлювати read-модель каталогу повторним читанням топіка `course.events` без доступу Query-контуру до PostgreSQL і зберігає порядок подій агрегата через ключ партиції.

Конфігурація, що реалізує рішення:

- Топіки `course.events`, `order.events` — 3 партиції, ключ `aggregateId`; `course.events` — `cleanup.policy=compact` (зберігається останній стан кожного курсу для replay).
- Producer: `acks=all`, `enable.idempotence=true`; публікація лише через Transactional Outbox ([SRS-FUN-15](../srs.md#srs-fun-15)).
- Consumer: ручний commit offset після успішної обробки; ідемпотентність — ключ `eventId` у Redis + `UNIQUE(event_id)` у PostgreSQL ([SRS-NFR-REL-02](../srs.md#srs-nfr-rel-02)); DLQ-топіки `<topic>.dlq`.

## Consequences (Наслідки)

### Позитивні

- Read-модель каталогу відновлюється з `course.events` без зв'язку Query-контуру із write-БД; ізоляція контурів CQRS зберігається.
- Додавання нового консюмера (наприклад, сервісу аналітики) не потребує змін у продюсерах.
- Порядок подій агрегата гарантується конфігурацією, а не кодом застосунку.

### Негативні та ризики

- **Складність повторів і DLQ.** Механізм retry з експоненційною затримкою та DLQ реалізується вручну в Order Service та Access Service; повтор у консюмері блокує партицію на час затримки (до 31 с сумарно). *Пом'якшення:* обмеження 5 спробами, моніторинг consumer lag ([SRS-NFR-OBS-01](../srs.md#srs-nfr-obs-01)).
- **Відсутність реплікації в локальному середовищі.** Один брокер з replication factor = 1 є єдиною точкою відмови. *Пом'якшення:* Transactional Outbox утримує неопубліковані події в PostgreSQL на час простою брокера ([SRS-NFR-REL-01](../srs.md#srs-nfr-rel-01)); у production-конфігурації — 3 брокери, `min.insync.replicas=2`. Обмеження зафіксовано у [SRS, розділ 1.3](../srs.md#13-межі-версії-out-of-scope).
- **Ресурсні витрати.** Kafka споживає ≈ 1–1,5 ГБ RAM з 16 ГБ еталонного хоста; час старту контейнера — 10–20 с, що збільшує тривалість інтеграційних тестів (Testcontainers) у CI.
- **At-Least-Once, а не Exactly-Once.** Kafka не гарантує exactly-once між БД консюмера та брокером; кожен консюмер зобов'язаний бути ідемпотентним. Помилка в реалізації ідемпотентності призводить до дублювання Access Grant.
- **FinOps у разі хмарного розгортання.** Керовані сервіси Kafka (Amazon MSK, Confluent Cloud) мають вищу мінімальну вартість, ніж керований RabbitMQ (Amazon MQ) за низького навантаження; у межах роботи розгортання хмарою не передбачено.
- **Vendor lock-in:** низький — Kafka є відкритим ПЗ (Apache 2.0), протокол підтримується Redpanda як сумісною альтернативою.
- **Поріг входу.** Необхідно опанувати модель партицій, offset та rebalancing consumer groups; некоректний commit offset є типовим джерелом втрати або повторної обробки подій.
