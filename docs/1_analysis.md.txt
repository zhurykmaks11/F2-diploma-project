# РОЗДІЛ 1. АНАЛІТИЧНИЙ ОГЛЯД ПРЕДМЕТНОЇ ОБЛАСТІ ТА СИСТЕМ-АНАЛОГІВ

## 1.2. Інженерний порівняльний аналіз програмних рішень-аналогів

У межах дослідження проведено системний технічний аналіз трьох репрезентативних програмних платформ, що реалізують механізми електронної дистрибуції цифрового контенту: Teachable, Shopify та WooCommerce.

### 1.2.1. Системно-архітектурний огляд аналогів

#### Teachable
Платформа розгорнута як хмарне SaaS-рішення, історично побудоване на сервісно-орієнтованій архітектурі (SOA) з фреймворком Ruby on Rails. Взаємодія між клієнтським застосунком і бекендом реалізована за допомогою синхронного протоколу REST API (HTTP/1.1). Основним транзакційним сховищем виступає реляційна СУБД PostgreSQL, доповнена Redis для черг Sidekiq. 
Критичним інженерним обмеженням системи є використання централізованого сховища для мутацій та аналітичних вибірок: під час одночасних запусків курсів спостерігається деградація продуктивності, зумовлена конкуренцією транзакцій за блоки оперативної пам'яті та дискового вводу/виводу.

#### Shopify
Програмна платформа функціонує за моделлю модульного моноліту з виділенням високопродуктивних сервісів мовами Go та Java. Зовнішні клієнтські точки входу використовують протоколи GraphQL та REST API, тоді як міжсервісна комунікація забезпечується за допомогою gRPC та брокера повідомлень Apache Kafka. 
Горизонтальне масштабування шару даних досягається завдяки розподіленому шардингу MySQL через рушій Vitess. Головним архітектурним компромісом є висока ресурсна вартість підтримки інфраструктури та надлишкова функціональна складність для сегмента виключно цифрових товарів.

#### WooCommerce
Монолітне вебрішення, інтегроване в CMS WordPress (PHP). Обмін даними побудовано на синхронному REST API без підтримки подієво-керованих магістралей. Збереження сутностей замовлень і товарів реалізовано в ненормалізованій реляційній структурі MySQL (`wp_posts`, `wp_postmeta`). 
Система демонструє критичні затримки (high latency) та транзакційні дедлоки під час обробки пікових потоків замовлень, оскільки операції читання сторінок і запису платежів блокують спільні таблиці СУБД.

### 1.2.3. Аналітичний висновок підрозділу 1.2

Аналіз виявив, що монолітні та класичні клієнт-серверні підходи зі спільною базою даних виявляються неефективними в умовах різкого зростання кількості одночасних операцій над цифровими активами через блокування на рівні читання/запису. 

У межах кваліфікаційної роботи передбачено реалізацію розподіленої подієво-керованої мікросервісної платформи на основі патерна CQRS. Відокремлення транзакційного контуру оформлення покупок (PostgreSQL) від оптимізованого кешованого контуру вибірки курсів (Redis) за асинхронної підтримки Apache Kafka дозволяє гарантувати масштабованість системи та стабільні показники затримки (Latency) за пікових навантажень.

## 1.4. Аналіз обраної предметної області в межах дослідження (модель As-Is)

Дослідження предметної області цифрової дистрибуції курсів та освітніх матеріалів дозволяє виділити таких ключових акторів: Студент/Покупець, Автор курсу/Інструктор, Платформний Адміністратор та Зовнішній Платіжний Шлюз[cite: 26]. Основними інформаційними сутностями є: обліковий запис користувача, цифровий актив (курс/матеріал), замовлення, платіжна транзакція та ліцензія на доступ[cite: 26].

Аналіз існуючих бізнес-процесів у стані «як є» (As-Is) виявив такі системні вузькі місця (Bottlenecks):
1. **Процес перегляду та пошуку каталогу:** Користувач здійснює запит на вибірку курсів. Синхронні важкі SQL-запити з багаторівневими об'єднаннями таблиць (JOIN) у спільній реляційній базі даних створюють високе навантаження на дискову підсистему та блокують таблиці, що призводить до лінійного зростання затримок (Latency)[cite: 9, 26].
2. **Процес оформлення замовлення:** У момент купівлі курсу виконується комплекс ACID-транзакцій у тій самій базі даних, яка обслуговує запити каталогу. Під час масових розпродажів це спричиняє конфлікти блокувань рядків (Deadlocks) та відмови в обслуговуванні транзакцій[cite: 9, 26].
3. **Процес надання цифрового доступу:** Системи часто використовують синхронне очікування підтвердження від платіжного шлюзу. У разі затримки мережі клієнт отримує таймаут (504 Gateway Timeout), а транзакція може залишитися в неконсистентному стані через відсутність механізмів гарантованої асинхронної доставки подій[cite: 26].

Додатково дотримуються регуляторні вимоги GDPR (право на видалення та знеособлення персональних даних) та стандарти безпеки PCI-DSS (ізоляція чутливих платіжних реквізитів)[cite: 26].

## 1.5. Постановка задачі та формування вимог (модель To-Be, Core Features, NFRs)

Цільова концептуальна модель (To-Be) передбачає ліквідацію виявлених деградацій монолітної архітектури шляхом переходу до розподіленої мікросервісної платформи із застосуванням патерна CQRS (Command Query Responsibility Segregation) та асинхронного брокера подій Apache Kafka[cite: 27]. Це забезпечує незалежне горизонтальне масштабування контурів читання (Query) та запису (Command) без взаємних блокувань[cite: 27].

### 1.5.1. Функціональні вимоги (Core Features)
* **Модуль автентифікації та IAM:** Автентифікація користувачів на базі протоколу OAuth 2.0 / JWT з реалізацією рольової моделі розмежування доступу (RBAC)[cite: 27].
* **Модуль каталогу (Query Side):** Фасетна фільтрація та високопродуктивний пошук курсів із використанням in-memory кешування у Redis[cite: 27].
* **Модуль управління замовленнями (Command Side):** Ізольована бізнес-логіка оформлення покупок із фіксацією доменних подій у механізмі Transactional Outbox[cite: 27].
* **Шина обміну повідомленнями (Kafka Pipeline):** Асинхронна трансляція подій (`OrderCreated`, `PaymentProcessed`) між сервісами з гарантією доставки[cite: 27].
* **Модуль активації доступу (Asset Delivery):** Автоматизована видача криптографічно захищених токенів доступу до матеріалів одразу після верифікації платежу[cite: 27].
* **Адміністративний модуль:** Вебпанель керування контентом та моніторингу стану розподілених черг[cite: 27].

### 1.5.2. Нефункціональні вимоги (NFRs Matrix)
* **Продуктивність та навантаження:** Цільова пропускна здатність системи має складати не менше 600 RPS[cite: 27]. Час відгуку Query API на 95-му перцентилі ($p95$) не повинен перевищувати 120 мс, а Command API — 250 мс[cite: 27].
* **Масштабованість та надійність:** Горизонтальне асиметричне масштабування сервісів у середовищі Docker; забезпечення моделі консистентності Eventual Consistency та гарантії доставки At-Least-Once з обробкою ідемпотентності через Redis[cite: 27].
* **Безпека:** Шифрування трафіку за протоколом TLS 1.3, використання підписаних токенів RS256 JWT, дотримання регламентів GDPR[cite: 27].

### 1.5.3. Постановка задачі
> *«Таким чином, метою кваліфікаційної роботи є проєктування та розробка хмароорієнтованої розподіленої платформи електронної комерції цифрових товарів та курсів на основі патерна CQRS та подієво-керованої архітектури для вирішення задачі усунення транзакційних конфліктів читання/запису, забезпечення гарантованої видачі цифрових активів та мінімізації затримок системи в умовах високих пікових навантажень.»*[cite: 27]
